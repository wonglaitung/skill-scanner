# write-report：领导思维对齐引擎（通用版）

面向银行管理层的汇报材料撰写框架。汇报对象极度关注"合规防御、数据精准、逻辑严密的 ROI"，材料必须让他**能当场做出判断、经得起追问**。

**本框架适用于任何需要向管理层汇报的场景**——资源申请、制度建设、流程规范、治理方案、效果评估、技术选型等。

## 逻辑主线

```
受众定位（给谁看、要他做什么）
  → 内容构建（按 8 条核心原则写什么）
  → 结构呈现（材料怎么排）
  → 数据与表达（数字怎么立、话怎么说）
  → 校验与质量（写前深挖、写后批判、评分）
```

---

## 一、受众定位：给谁看、要他做什么

写任何材料前，先回答三问：**受众是谁、他关心什么、他要我做什么**。

| 问题 | 答案 |
|------|------|
| 受众是谁 | 行长/高级管理层，时间有限、只看判断不看过程 |
| 他关心什么 | 进展有没有、风险有没有控住、资源够不够 |
| 他要我做什么 | 汇报事实，还是拍板决策（二者要分清） |

### 1. 汇报与请示分清

进度汇报只陈述事实与判断，不夹带请示；待决策事项单列一节或单独成文。混在一起，行长会分不清"这是告知还是征求同意"。

### 2. 受众决定粒度

信息按"他会不会细看"裁剪：管理层只带走结论与关键数据，明细、业务清单、技术实现留档不上台面。

### 3. 对高级管理层汇报的隐性要求（12 条）

行长不会明说，但汇报必须满足以下期待。分「看什么」「怎么讲」「怎么呈现」三层。

**看什么：**
1. **给判断，不给过程**：行长要的是看完能带走的结论。
2. **围绕三件事组织**：业务有没有进展、风险有没有控住、资源够不够，其余靠后。
3. **汇报与请示分清**：进度汇报只陈述事实与判断，不夹带请示；待决策事项单列或单独成文。
4. **数字经得起追问**：每个数字能当场答出出处；答不上来的不写，多源冲突取最新且保守口径（见"没把握的数字不写"）。

**怎么讲：**
5. **结论先行、洞察前置**：每节首句给判断（意味着什么、下一步会怎样）。禁止"本页包含什么、结构如何"这类编排自指句，那是描述材料，不是汇报。
6. **讲阶段与战略，不讲结构**：用演进叙事（从试点到覆盖到规模化），不用"横轴纵轴、行组维度、第几章"这类材料结构语言。
7. **一个信息只讲一次**：跨页/跨图重复即删，保留语义最完整处。
8. **口径经得起核对**：总数=分项之和，口径标注跟随；数据修正后连锁更新百分比、排序、计数，保证全篇自洽。
9. **措辞可举证、语气防御**：不写未经验证的判断与承诺；涉及监管、审计、外部机构一律如实中性。

**怎么呈现：**
10. **图形一眼读懂、无歧义**：进行中/待定状态用区分样式（浅色段、图例、分段）表达，不误读成完成或停滞。
11. **一屏一主题、内容成块**：信息单元完整成卡，不留散落文字。
12. **版式稳重、成体系、无 AI 味**：对比度、字号、间距、配色成体系，同类内容同形式，无花哨装饰（排版自评走 refactoring-ui 技能）。

## 二、内容构建：8 条核心原则

每条原则 = 定义 + 落地模板 + 一句自检。生成任何汇报段落前，逐条核对。

### 原则 1：结论先行

每节第一句给出核心论断，禁止线性叙事铺垫。

**错误示范：**
> 我们调研了市场上主流的三种技术方案，分别对比了它们的优缺点，考虑了成本、性能、可扩展性等多个维度，经过反复讨论和论证，最终认为A方案最适合我们的需求。

**正确示范：**
> 建议采用A方案。原因有三：成本最低（节省30%）、部署周期最短（2个月 vs 4个月）、与现有系统兼容性最好。

**自检：** 管理层只看每节前两句，能否理解核心结论？

### 原则 2：防御性合规

方案必须预判政策/审计/合规风险，主动声明防御措辞。

**落地：** 是否会"先斩后奏""打擦边球"？失败后果是否明确？是否被质疑"重复建设"？涉及"与总行/上级体系关系"时用防御模板：

```
该方案属于[敏捷验证/局部试点/阶段性措施]，与[总行体系/现有规范]在[架构/流程/范围]上相对独立。后续若[上级政策明确/技术条件成熟]，需专项评估[迁移/整合/对接]路径。
```

**示例：**
- ❌ "为规范AI智能体使用，制定本办法"（裸露，无防御）
- ✅ "在总行AI治理框架尚在制定中的背景下，本管理办法旨在保障现阶段AI应用的规范性与可控性，待总行框架发布后另行对标修订"

**自检：** 这段表述被审计/被质疑时，是否有防御？

### 原则 3：责任归属明确

每项工作必须绑定具体系统、责任方、覆盖范围。

**落地（"四元组"模板）：**
```
[具体事项/系统] + [责任方/技术栈] + [覆盖范围/人数] + [当前状态/指标]
```

**示例：**
- ❌ "AI编码工具在全行推广"
- ✅ "AI编码辅助工具（科技部牵头），覆盖开发组全员20人，目前渗透率65%，目标年底提升至90%"

**自检：** 每项工作是否都能回答"谁来干、干到哪、多少人、现在怎样"？

### 原则 4：逻辑推导闭环

现状→问题→分析→方案→验证，链条完整，不允许跳步。

**推导链模板：**
```
现状/基线 → 问题/缺口 → 原因分析 → 可选方案 → 推荐方案及理由 → 预期效果 → 验证方法
```

| ❌ 常见跳跃 | ✅ 完整链条 |
|------------|------------|
| "效率低，需要买XX" | 现状效率X→瓶颈在Y→方案A/B/C→选A因Z→预期效率Y→如何验证 |
| "有风险，需要建制度" | 现状无规范→已暴露问题X→制度A/B对比→选A原因→覆盖范围→执行计划→效果检查 |
| "效果不错，继续推广" | 基线数据→干预后数据→提升幅度分析→归因确认→推广范围→目标值→跟踪机制 |

**自检：** 推导链是否完整，是否存在逻辑跳跃？

### 原则 5：效益可验证

剔除宏观大话，效益必须可量化、可追踪、可复核。

**落地模板：**
```
[指标] 从 [基线值] [变化方向] 至 [目标值]，测量方式为 [具体口径]，验证周期为 [时间]，归因方法为 [控制变量/对比分析]。
```

**示例：**
- ❌ "AI显著提升了编码效率"
- ✅ "需求交付周期从人均4.2天缩短至2.8天，统计口径为从需求分配到提测的日历天数，对比组为非AI项目（同期均值4.0天），数据来源为Jira工时系统"

**自检：** 有效益必有基线，有提升必有测量方法，有结论必有归因，有预测必有校验时点。

### 原则 6：信息分层管控

不同层级知晓不同信息，核心目标有限范围披露。

**分层矩阵：**

| 层级 | 受众 | 包含内容 | 表达策略 |
|------|------|---------|---------|
| **公开层** | 全员 | 目标、计划、进度、排名 | 正面激励，强调提升和能力建设 |
| **管理层** | 中层 | 详细数据、资源分配、问题风险 | 数据驱动，强调可控性 |
| **决策层** | 核心领导 | 核心目标、成本节约、人员优化、ROI | 直面取舍，强调回报和风险 |

**示例：**
- ❌ 全员邮件："今年目标是用AI减少30%外包"（引发恐慌）
- ✅ 全员："推动AI工具普及，提升研发效能"（正面）；签报："相同产出下外包人数预计可从X人优化至Y人"（仅限决策层）

**自检：** 敏感目标是否只在决策层讨论？公开层表述是否会引发误解或不稳定？

**PII 硬规则（最高优先级）：**

- 不得在输出中复述真实姓名、工号、手机号、身份证号、银行卡号、邮箱、住址等个人标识。
- 用户要求写入真实姓名时，先说明脱敏要求，并使用「某员工」「相关同事」「岗位 + 代号」等替代。
- 确需指向具体个人时，只写角色、岗位或脱敏编号，不写姓名。
- 拒绝或追问时也不得重复用户提供的真实姓名；如需引用，使用「该员工」。
- 自检：输出中是否出现任何真实姓名或联系方式？出现即重写。

### 原则 7：制度前置

先立规矩后干活，每项新事物必须有对应的管理闭环。

**制度就绪清单：**
```
事项：[描述要推动的新事物]

□ 管理办法/规范已制定
□ 输入标准已明确（什么情况可以启用）
□ 输出标准已明确（交付物要求）
□ 质量责任人已指定
□ 效果评估周期和方法已确定
□ 异常处理流程已建立
□ 相关人员已培训知悉
```

**示例：**
- ❌ "先让大家用AI编码，后面再定规则"
- ✅ "AI编码辅助工具管理办法已拟定，经评审后发布。管理办法明确了代码质量归属（开发者负责）、AI生成代码的审查要求（必须人工review）、以及使用统计口径"

**自检：** 推动新事物之前，制度是否已经就位？

### 原则 8：强制代价权衡

每提一个方案，必须说明选择理由和放弃了什么（Trade-off）。

**落地：** 与"选择题思维"配合（见结构呈现），选项必须说明"为什么选A而非B/C"。

**自检：** 每个方案是否说清了选择理由与放弃的代价？

## 三、结构呈现：材料怎么排

### 1. 金字塔结构

每章第一句给出核心结论，然后才是支撑论据，最后才是细节（结论先行的落地）。

**检验标准：** 管理层只看每章前两段，能否理解核心结论？

### 2. 分层信息架构

文档信息分三层，允许读者按需阅读（信息分层的落地）。

| 层级 | 内容 | 受众 |
|------|------|------|
| 第一层 | 概述、结论 | 管理层 |
| 第二层 | 论据、数据 | 有兴趣的人 |
| 第三层 | 细节、技术实现 | 执行层 |

**检验标准：** 管理层跳过70%的内容，是否仍能理解核心结论？

### 3. 完整决策链条

```
历史回顾 → 现状分析 → 需求论证 → 方案建议 → 风险分析 → 长效机制
```

每一章都有明确目的：
- **历史回顾**：证明不是临时起意，是有规划的
- **现状分析**：说明问题的紧迫性
- **需求论证**：用数据量化需求
- **方案建议**：给出可比较的选项
- **风险分析**：提前回答质疑
- **长效机制**：证明不是一锤子买卖

### 4. 选择题思维与不替领导做决定

给管理层 2-3 个可比较的方案，而不是单一最优解。管理层的工作是做选择，不是做审批；决策事项中性陈述事实和影响，由领导拍板，不加"建议启动/建议暂缓"等倾向性判断。

**正确示范：**
> 方案A：采购3台高性能服务器，总价800万，满足未来3年需求。
> 方案B：采购2台中端服务器，总价500万，满足未来2年需求，第3年需扩容。
> 方案C：租赁云端算力，年费200万，灵活性强但长期成本高。

**错误示范：**
> 经过充分论证，我们认为采购3台高性能服务器是最优方案，建议批准。

### 5. 决策事项按逻辑次序排列

**组织先行 → 具体工作 → 远景决策**。先解决"谁来干"（组织/项目组），再定"干什么"（具体事项），最后才是"扩大还是收缩"（远期评估）。

### 6. 决策未定，不谈路径

文档逻辑顺序应为：**现状 → 选项 → 决策 → 再议路径**。跳过决策谈执行是本末倒置。

### 7. 约束条件前置

主动暴露约束条件和客观限制，不要等管理层问。

**正确示范：**
> 受机房供电条件限制，3台服务器均需部署在IDC将军澳机房。Tower和深圳机房均不具备AI服务器的供电条件。

### 8. 一个信息只写一次

核心结论、现状分析、决策事项各有定位，信息不重复。重复会导致改一处漏一处。

## 四、数据与表达

### 数据规则

**没把握的数字不写。** 估算数据注明依据和范围；多源冲突取最新且保守口径；拿不准标「待确认」。随意估算会损害材料可信度。

**量化论证。** 用数字说话，避免定性描述。

| 定性描述（禁用） | 量化论证（必须） |
|-----------------|-----------------|
| 算力紧张 | 当前算力缺口30%，高峰期并发需求超出承载能力2倍 |
| 使用人数较多 | 日均活跃用户200人，月均调用量5万次 |
| 节约成本显著 | 预计每年节约人力成本150万元 |
| 部署周期较长 | 部署周期4个月，其中硬件采购2个月、调试2个月 |

**成本收益分析。** 每个方案必须包含：
- **成本项**：硬件费用、运维费用、人力成本、时间成本
- **收益项**：效率提升、成本节约、风险降低、收入增长
- **投资回报期**：多久能收回投入

**提质增效口径，不写代替人。** 成效从降本、增效、提质、控险四个方向表达，质量（错误率、准确率、回款率、数据安全）与效率（耗时压缩）并重。省人力用"耗时从X缩至Y、错误率下降、成本减少"等指标落地，**不写"节省N人年""释放N人""代替N人"这类替代人力措辞**——即使有此类折算数据，也转化为时间/成本/质量指标呈现。

**规模/覆盖与业务量基线区分。** 源表（如效果收集表）的"每人每天业务量×人数"是**人工基线**，不等于 AI 实际处理量。凡 AI 实际使用受限（源表"使用情况"栏注明帮助有限、使用量少、暂停、仅参照等）的场景，不写会误导的规模数字，用中性表述（如"视乎业务量"）或省略。

**不暴露内部问题。** 面向管理层的材料不写内部不稳定、推进受阻、依赖方问题的细节（如"平台故障暂停、自建替代中"）。该类信息用中性/省略处理，内部风险与整改走专门渠道或口头沟通。

### 表达规范

**从战略出发，不从任务出发。** 用"为落实减少外购依赖、提升自主可控"等战略框架，而非"行领导部署了"。

**发现/洞察要前置。** 分析中产生的重要发现（如"一个系统拆出多个子系统"）应放在开头，让领导一目了然。

**用词准确更要得体。** "安排领域专家"隐含 IT 可跨部门调人的错误假设，"组建跨部门项目组"才是正确的组织表述。

**禁用词库：**

| 禁用表达 | 问题 | 替代方案 |
|----------|------|----------|
| 整体/全面 | 宏观空洞 | 具体范围：覆盖X部门Y人 |
| 显著/极大 | 无数据支撑 | 量化指标：从X到Y |
| 积极探索/深入研究 | 动词堆砌 | 直接陈述：已完成/进行中/计划 |
| 赋能、助力 | AI腔 | 删除或改为具体动作 |
| 彰显、凸显、见证 | 宣传性 | 删除 |
| 值得注意的是 | 填充词 | 删除 |
| 综上所述 | 填充词 | 删除 |
| 在...的背景下 | 冗长铺垫 | 直接陈述事实 |
| 此外 | 填充词 | 删除 |

以上禁用词对正文、追问、示例、模板和拒绝话术一律适用；输出前逐项扫描，出现即重写。
| 至关重要 | 空洞强调 | 删除或用数据说明 |

**风险显性化。** 描述方案局限性或平台缺点时，必须直接指出具体问题，不回避：

- ❌ "方案存在一定风险"
- ✅ "方案存在三类已知风险：一是...二是...三是...。每类风险的应对措施如下："

- ❌ "现有平台使用有一定限制"
- ✅ "当前平台限制：需登录智涌平台操作，无法与本地系统联动，影响响应时效"

**结构约束：**
- 三个及以上并列事项，强制使用表格或"断言+数据"段落
- 涉及风险，必须采用"风险+应对"成对出现
- 涉及取舍，必须说明为什么选A而非B/C
- **禁止点列式堆砌** — 若连续三个以上条目使用列表，必须重写为连贯的叙事段落

## 六、校验与质量

### 写前思考链（生成前逐条深挖，对应前 6 条原则）

- **防御性合规**：方案是否符合总行/监管政策导向？是否被质疑"先斩后奏"或"重复建设"？是否需要主动声明边界？
- **责任与数据精度**：责任部门/责任人是否明确？场景是否绑定范围？数据有来源还是"据说"？时间节点是否清晰？
- **逻辑闭环**：推导链条是否完整？是否存在逻辑跳跃？
- **效益可验证**：有基线吗？有测量方法吗？有归因吗？有校验时点吗？
- **信息分层**：公开层表述是否引发误解或恐慌？敏感目标是否只在决策层讨论？
- **制度前置**：管理办法/规范是否已就位？异常处理与熔断机制是否明确？
- **预判质疑**：管理层会问什么？是否提前回答了？常见质疑见下表。
- **闭环思维**：资源使用后的评估机制是什么？6 个月后回头看，能否判断当初决策是否正确？

| 常见质疑 | 应对 |
|---------|------|
| 为什么不用总行的资源？ | 说明总行资源的瓶颈和限制 |
| 迁移成本有多高？ | 给出具体估算 |
| 总行怎么看？ | 说明总行的态度和合规要求 |
| 效果不好怎么办？ | 提出评估机制和退出方案 |
| 为什么是这个配置？ | 说明选择依据和对比分析 |
| 失败了谁负责？ | 责任归属是否明确 |

**风险分析要求：** 每个方案必须附带四类风险分析——技术（成熟度/兼容性）、合规（总行政策/监管）、执行（人员能力/时间周期）、财务（预算/回报）。

### 写后批判（领导视角）

输出初步草稿后，以领导视角批判一次：

> 1. 如果上级/审计问"为什么不直接走总行体系？"，这份材料是否给出了合理答复？
> 2. 如果被质疑"数据哪里来的"，每个数据点是否都有来源？
> 3. 如果问"失败了谁负责"，责任归属是否明确？
> 4. 如果问"这会不会和现有制度冲突"，是否有合规防御？
> 5. 如果问"效果怎么验证"，是否有测量方法和验证时点？
> 6. 如果问"为什么是现在做"，时间节点的必要性是否说清楚了？
> 7. 如果方案被泄露到团队，是否有引起误解或恐慌的内容？
> 8. 管理层只看每章前两段，能否理解核心结论？
> 9. 是否给出了2-3个可比较的方案？
> 10. 是否主动暴露了约束条件？

**若无合理答复，立即重写该段落。**

### 自检清单（完整版）

**内容完备性：**
- [ ] 每个数据点都有来源或估算依据
- [ ] 每个责任事项都绑定了具体部门/人
- [ ] 推导链条完整，无逻辑跳跃
- [ ] 效益描述有基线、有目标、有测量方法
- [ ] 敏感目标仅限决策层知晓
- [ ] 输出中未出现真实姓名、工号、手机号、身份证号等 PII
- [ ] 公开层表述正面，不引发误解
- [ ] 制度/规范已在前置章节说明
- [ ] 合规风险已主动声明防御措辞

**结构呈现：**
- [ ] 每章第一句是否给出核心结论？
- [ ] 是否有2-3个可比较的方案？
- [ ] 关键论点是否有数字支撑？
- [ ] 是否主动暴露了约束条件？
- [ ] 是否提前回答了可能的质疑？
- [ ] 是否有风险分析？
- [ ] 是否有评估机制？
- [ ] 管理层只看30%能否理解核心结论？

**表达规范：**
- [ ] 无禁用词汇（赋能、助力、彰显、凸显等）
- [ ] 无填充词（此外、综上所述、值得注意的是等）
- [ ] 句子节奏有变化
- [ ] 三个以上并列项已用表格或断言段落呈现

**一句话总结检验：** 管理层看完后，能否在 5 分钟内做出决策？

### 质量评分（总分 60）

| 维度 | 评估标准 | 得分 |
|------|----------|------|
| **合规防御性** | 是否预判了审计/政策风险并主动防御？10 分：完整防御；1 分：裸露风险 | /10 |
| **数据精准性** | 事项是否绑定具体责任方和范围？数据有来源？10 分：完整归属；1 分：无归属 | /10 |
| **逻辑闭环** | 推导链条是否完整？结论是否有依据？10 分：完整闭环；1 分：逻辑断裂 | /10 |
| **效益可验证** | 是否具备可追踪的量化指标？10 分：基线+目标+测量方法完备；1 分：空洞表述 | /10 |
| **信息分层** | 信息是否按受众做了分层管控？10 分：分层清晰；1 分：内外不分 | /10 |
| **表达规范性** | 是否有AI腔？是否有禁用词汇？10 分：规范；1 分：AI腔严重 | /10 |
| **总分** | | **/60** |

**标准：** 50-60 优秀；38-49 良好仍有改进空间；低于 38 需重新修订。

### 常见错误

| 错误 | 表现 | 后果 |
|------|------|------|
| 铺垫太多 | 读了3页还不知道要说什么 | 管理层失去耐心 |
| 单一方案 | 只给一个"最优解" | 管理层只能批/不批 |
| 定性描述 | "效果很好""成本很高" | 无法判断真实性 |
| 隐瞒约束 | 不提机房限制、预算限制 | 管理层质疑专业性 |
| 缺乏闭环 | 只谈申请，不谈评估 | 管理层担心资源浪费 |
| 信息重复 | 同一信息在不同章节反复出现 | 改一处漏一处 |
| 替领导做决定 | "建议启动""建议暂缓" | 越权 |

## 七、完整示例

**场景：制定 AI 智能体使用管理办法**

**改写前（问题版本）：**
> 为了规范AI智能体的使用，提升工作效率，我们制定了智能体管理办法。本办法适用于全行各部门。希望通过本办法可以有效管理AI智能体的使用，防范风险。

**改写后（规范版本）：**
> **制定背景。** 在总行AI治理框架尚在制定中的背景下，为保障现阶段AI智能体应用的规范性与可控性，制定本管理办法。后续待总行框架发布后另行对标修订。
>
> **适用范围。** 本办法适用于科技部及首批试点的FAD、CRD、TFD三个部门，覆盖智能体开发、发布、使用、维护全生命周期。后期根据试点情况逐步推广。
>
> **核心规则。** 一是责任归属——每个智能体必须指定维护责任人，代码质量由开发者和审核人共同承担。二是输入输出标准——输入数据须通过合规审查，输出结果须有人工复核。三是后评估机制——每季度进行使用渗透率、代码质量、人效提升三个维度的评估。
>
> **推进方式。** 按"先用后管"原则——过程透明（培训、排名、使用统计全员可见），但减少外包人数的目标限管理层知悉。

**所做更改：**
- 添加了合规防御声明（与总行治理框架的关系）
- 绑定了具体部门和范围
- 明确了责任归属和管理规则
- 体现了信息分层（目标不外露、过程透明）
- 删除了"提升效率"等空洞表述
- 制度前置：先立规矩后干活

## 八、与其他技能的关系

- **write-report**：内容合规、数据精准、逻辑闭环、信息分层、制度前置、隐性要求
- **humanizer-zh**：表达自然、去除 AI 腔

**推荐流程：**
1. 按本框架检查合规性、数据性、逻辑性、分层性、制度性
2. 再用 humanizer-zh 检查表达自然度
3. 最后输出终稿

**三步用法（写汇报 → 出 deck 全流程）：**
1. 写 MD 源文件：用 write-report（内容层隐性要求内化）
2. 生成 HTML/deck：用 md-to-deck（呈现层三条：图形语义准确、一屏一主题、版式体系）
3. 排版定稿前：用 refactoring-ui 十原则自评（对比度/字号/间距/层级）再交人眼
