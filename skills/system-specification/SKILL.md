# 系统规格书编写要求

规格书的目的是指导自研替代系统的开发，必须从"业务概念描述"升级为"可实施的技术规格"。

## 核心原则

- **可实施性优先**: 每个规格项都必须具体到可以直接编码实现，不能停留在概念描述
- **公式和示例**: 涉及计算的模块必须给出公式和数值示例，不能只描述"计算逻辑"
- **接口协议**: 涉及外部集成的模块必须给出具体的协议、端口、数据格式
- **状态定义**: 涉及状态流转的模块必须给出完整的状态机定义和守卫条件
- **配置参数**: 涉及部署运维的模块必须给出可直接使用的配置参数表
- **术语解释**: 涉及业务领域的专业术语必须给出中英文定义、业务意义和系统表现
- **英文简称说明**: 所有英文缩写（如 OMS、EMS、FIX、NAV、HWM、TA、PB、UTI 等）在文档中首次出现时必须给出英文全称和中文翻译，且在术语表中集中登记

## 12 项具体要求

### 1. 交易全生命周期追踪

- 必须完整描述交易从创建到结算的全过程
- 必须定义所有状态维度及其独立转换逻辑（如 CancelAmend、ContractStatus、SettlementStatus、MatchedStatus、ConfirmedStatus）
- 每个状态转换必须有守卫条件（guard conditions）
- 必须提供典型场景的完整生命周期示例（如买入→持有→卖出、卖空→回补）
- **Why**: 自研系统必须精确复现原系统的多维度状态追踪能力，不能简化为单一状态字段
- **How to apply**: 每个涉及状态流转的模块，都要画出完整的状态机图，列出所有合法转换路径和守卫条件

### 2. 买卖原因与持仓计算关系

- 必须列出所有 BuySellReason 代码及其精确含义（B/BC/BTC/BTO/S/SS/STC/STO/SUBS/REDM 等）
- 必须给出持仓计算公式，明确不同买卖原因对持仓的影响
- 必须区分开仓、平仓、回补等操作对持仓方向和数量的不同影响
- **Why**: 持仓计算是 P&L 的基础，买卖原因的误判会导致整个盈亏体系错误
- **How to apply**: 每个涉及持仓变动的场景，都要给出具体的计算公式和数值示例

### 3. 外部系统对账机制

- 必须描述与 PB（主经纪商）、托管人等外部系统的对账流程
- 必须定义文件交换机制（IncomingFile/OutgoingFile 格式和处理流程）
- 必须描述对账差异的识别和处理方式
- 必须包含对账摘要（Reconciliation Summary）的数据结构和展示逻辑
- **Why**: 对账是运营风险控制的关键环节，缺失对账能力会导致资金和持仓数据不可信
- **How to apply**: 每个外部数据接入点，都要定义对应的对账机制和差异处理流程

### 4. 外部系统集成配置细节

- 必须给出每个外部集成的具体参数：协议、端口、数据格式、认证方式
- 市场数据源（如 Bloomberg ServerAPI/DataLicense、Reuters DSS、Datahub）必须列出端口和接口协议
- 交易接口必须定义来源标识（如 H/T/X/D/P）及其对应的系统
- FIX 协议必须指定版本和消息映射
- 文件传输必须指定协议（FTP/SFTP/SMTP）和目录结构
- 认证必须描述具体机制（如 LDAP 配置参数）
- **Why**: 自研系统需要无缝对接现有基础设施，缺少具体参数会导致集成无法实施
- **How to apply**: 每个外部集成点，都要提供可直接用于配置的参数表（协议、地址、端口、认证、数据格式）

### 5. 运维与部署层面的具体参数

- 规格书不能只停留在业务逻辑层面，还必须覆盖部署和运维所需的配置参数
- 必须包含服务端口汇总、数据库连接方式、认证机制等运维细节
- 必须定义监控和健康检查机制
- **Why**: 开发团队需要知道系统如何部署和运维，而不仅仅是业务逻辑
- **How to apply**: 规格书必须包含独立的部署架构章节，提供可直接用于运维的配置清单

### 6. 数据完整性与事务边界

- 每个写操作必须明确事务边界（哪些操作必须在同一事务内）
- 跨服务操作必须定义补偿机制（而非只写"回滚"）
- 必须定义事务隔离级别（如 MShare 分配使用可序列化隔离）
- 必须定义自治事务日志的适用场景（主事务回滚但日志保留）
- **Why**: 金融系统中事务边界定义错误会导致资金数据不一致，"回滚"二字不足以指导实现
- **How to apply**: 每个涉及多步写操作的流程，都要标注事务起止点、隔离级别、失败补偿策略

### 7. 边界条件与异常场景

- 每个计算模块必须定义边界条件（零值、负值、空值、溢出、除零）
- 每个状态转换必须定义非法转换的处理方式（而非只画合法路径）
- 必须定义数据缺失时的默认行为（null 字段如何处理、引用数据不存在时如何处理）
- 必须定义并发冲突的具体场景和解决策略
- **Why**: 边界条件是开发中最容易出 bug 的地方，现有规格书几乎零覆盖
- **How to apply**: 每个计算公式和状态机，都要补充"当 X 为空/零/负/冲突时"的处理规则

### 8. 数据迁移与历史数据兼容

- 必须定义新旧系统的数据映射关系（字段级，不是表级）
- 必须定义历史数据的格式差异和转换规则
- 必须定义双跑期（parallel run）的数据对齐策略
- 必须定义迁移验证的校验规则（记录数对比、金额对比、抽样核对）
- **Why**: 数据迁移停留在阶段划分层面无法实施，字段级映射才是开发真正需要的
- **How to apply**: 每个核心数据表，都要提供字段级的新旧映射表和转换规则

### 9. API 契约完整性

- 每个 API 必须定义完整的请求/响应 schema（包括所有可选字段和默认值）
- 列表 API 必须定义分页上限、默认排序、最大返回条数
- 必须定义幂等性要求（哪些操作需要支持幂等、通过什么机制实现）
- 必须定义限流策略（每用户/每接口的 QPS 限制）
- **Why**: API 契约不完整会导致前后端反复对齐，幂等和限流缺失会导致生产事故
- **How to apply**: 每个 API 端点都要有完整的 JSON schema，标注必填/可选/默认值/约束

### 10. 可测试性要求

- 每个核心业务规则必须附带可执行的测试用例（给定输入→预期输出）
- 必须定义与原系统的对齐验证方法（相同输入→相同输出）
- 必须定义关键路径的集成测试场景（端到端业务流程）
- 必须定义性能基线（关键操作的响应时间上限）
- **Why**: 规格书最终要能验证"开发是否正确"，没有验收标准就无法判断实现是否正确
- **How to apply**: 每个核心业务规则，都要提供至少一组 Given-When-Then 测试用例

### 11. 专业术语表要求

- 规格书必须包含专业术语表章节，解释业务领域的核心概念
- 每个专业术语必须包含：术语名称（中英文）、定义、业务意义、应用场景、数值示例（如适用）
- 对于复杂概念（如结晶化、均等化），必须提供通俗易懂的比喻解释
- 术语定义必须面向开发人员，不能只停留在概念描述，要说明其在系统中的具体表现
- 必须涵盖系统特有的专业术语，不能假设读者已具备金融领域知识
- **Why**: 开发团队可能不熟悉金融领域术语，缺少术语解释会导致理解偏差和实现错误
- **How to apply**: 为每个系统规格书添加独立的"术语表"章节，按业务模块分组

**示例术语表格式**:

| 术语 | 英文 | 定义 | 业务意义 | 系统表现 |
|------|------|------|----------|----------|
| 结晶化 | Crystallization | 在特定日期锁定HWM并实际收取累积的业绩费 | 保护投资者利益，管理人只能对超额收益收费 | Fund.LastCrystallizationDate, Fund.FundHwm 字段 |

### 12. 英文简称说明要求

- 每个英文缩写（如 OMS、EMS、FIX、NAV、HWM、TA、PB、UTI、ETF、OTC、FX 等）在文档中首次出现时，必须标注英文全称和中文翻译
- 示例格式：**OMS** (Order Management System，订单管理系统)
- 必须在文档附录的术语表中集中登记所有使用的缩写
- 不要假设读者熟悉金融/IT行业的英文缩写
- **Why**: 英文缩写是文档阅读的最大障碍之一，尤其对不熟悉金融领域的开发人员
- **How to apply**: 每次引入新缩写时，遵循"首次出现必解释、术语表必登记"原则
